# ADR-015: Monorepo layout and tooling

- **Status:** Accepted (MOH-18)
- **Date:** 2026-11-07
- **Deciders:** Platform engineering
- **Related:** [System architecture §4](../architecture/system-architecture.md#4-code-organization),
  constitution Principles V–VI, ADR-001 (Cargo workspace modules), ADR-002 (backend tooling),
  ADR-003 (frontend structure), ADR-012 (generated client)

## Context

The product has a Rust backend, an Angular dashboard, an embeddable widget, infrastructure and
operations scripts, load tests, specs and documentation. They change together often: an API change
touches the backend handler, the OpenAPI document, the generated client and the dashboard
feature in one piece of work.

The decision has to balance these forces:

- **Atomic changes.** A contract change and its consumers should land in one PR, reviewed and
  tested together.
- **CI cost.** A docs-only change shouldn't run a 30-minute Rust build; a frontend change
  shouldn't run backend integration tests.
- **Discoverability.** Contributors (and agents) need one obvious place for each kind of file.
- **Tooling per language.** Rust and Node have their own package managers and build tools; one
  meta-build system on top adds complexity.

## Decision

### 1. One repository, top-level directories by concern

```text
backend/      Rust Cargo workspace (ADR-001/002): crates/{server or apps/*, modules/*, shared/*},
              migrations/, rust-toolchain.toml
frontend/     pnpm workspace: apps/dashboard (Angular), apps/widget (ADR-011), libs/* (only
              libraries with real consumers), e2e/ (Playwright)
infra/        Docker Compose (local, staging), Dockerfiles, Caddy, observability configs
ops/          Operational scripts: deploy, rollback, backup, restore, verification
loadtest/     k6 scripts and budgets
docs/         architecture/, adr/, security/, runbooks and configuration
specs/        Spec Kit feature specs (spec → plan → tasks); .specify/ holds the constitution
.github/      CI workflows, PR template, CODEOWNERS
```

Nothing else at the repository root except standard files (`README.md`, `CONTRIBUTING.md`,
`AGENTS.md`/`CLAUDE.md`, licence, editor and tool configs). Local helper scripts, logs and
reference artefacts don't belong in version control.

### 2. Native tooling per ecosystem, no meta-build system

| Area | Tooling |
| -- | -- |
| Backend | `cargo` workspace; `rustfmt`, `clippy -D warnings`, `cargo test`, `cargo audit`, `cargo-deny`; toolchain pinned in `rust-toolchain.toml` |
| Frontend | **pnpm** workspace with a committed lockfile; Angular CLI builds; ESLint + Prettier; Vitest/Angular unit tests; Playwright e2e; Node version pinned (`.nvmrc` / `packageManager`) |
| Contract | OpenAPI document generated by the backend; TypeScript client generated into the frontend (ADR-012) |
| Specs | Spec Kit commands and templates under `.specify/` |
| Local services | `infra/docker-compose.yml` (Postgres + pgvector, Redis, MinIO with bucket bootstrap, Mailpit; the same file is the base of the staging stack) |

A top-level task runner (`justfile` or `Makefile`) provides the common entry points
(`just dev`, `just test`, `just lint`, `just gen-client`) by calling the native tools. It holds no
build logic of its own.

### 3. CI per area, triggered by paths

- Separate workflows for backend, frontend and docs, each with **path filters** (`backend/**`,
  `frontend/**`, contract files) so unaffected areas skip.
- A contract change (OpenAPI document) triggers both backend and frontend.
- A required **gate job** aggregates results so branch protection has one stable check even when
  some workflows skip.
- Actions are pinned by commit SHA; caches for Cargo and pnpm stores.

### 4. Ownership

`.github/CODEOWNERS` maps directories to owners (backend modules, frontend apps, infra, security
docs), so reviews route automatically.

## Alternatives considered

| Option | Why rejected |
| -- | -- |
| **Polyrepo** (backend, frontend, widget, infra separately) | Contract changes span repositories and need coordinated, versioned releases. Too much overhead for one team. |
| **Nx / Turborepo / Bazel as the build system** | Good affected-graph builds, but Nx and Turborepo are Node-centric (Rust support is plugin-based), and Bazel's cost is high for a small team. Path-filtered CI gets most of the benefit. Revisit if CI time becomes a measured problem. |
| **npm or Yarn instead of pnpm** | pnpm's strict, content-addressed store avoids phantom dependencies and is fastest in CI. |
| **Frontend inside the Cargo workspace directory, or the reverse** | Mixes toolchains and confuses both ecosystems' tooling. |

## Consequences

**Positive**

- API, client and UI change in one reviewed PR.
- Each ecosystem uses its standard tools; nothing exotic to learn.
- CI time scales with what changed, not with the repository.

**Negative and costs**

- Path filters must be kept accurate, or a change can skip a check it needed (mitigated by the
  gate job and running everything on `master`).
- One repository's history and permissions cover everything; fine-grained access would need
  CODEOWNERS plus branch rules.
